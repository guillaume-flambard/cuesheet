Oui. Je vais te faire un **document maître**, pensé pour être donné tel quel à ton autre agent. Il doit lui permettre de reprendre CUESHEET sans reconstruire la conversation ni transformer toutes les idées en chantiers immédiats.

Le point essentiel à préserver est : **la vision est immense, mais le critical path actuel est volontairement étroit.** Tout ce qui suit définit le produit ; ça ne signifie pas « implémente tout maintenant ».

# CUESHEET — MASTER PRODUCT & ARCHITECTURE DIRECTION

## 0. Pourquoi ce document existe

CUESHEET a accumulé beaucoup d'idées, de concepts et de primitives. Le risque actuel est double :

1. perdre la vision globale et revenir vers « un OpenCode amélioré » ;
2. transformer chaque nouvelle idée en chantier immédiat et ne jamais atteindre le dogfooding.

Ce document fixe donc :

- ce qu'est CUESHEET ;
- ce qu'il ne doit surtout pas devenir ;
- son modèle mental ;
- ses concepts fondamentaux ;
- sa direction UX ;
- son architecture agentique ;
- sa gestion du contexte, des modèles et des ressources ;
- sa vision entreprise ;
- sa stratégie de preuve ;
- sa direction self-hosting ;
- les idées futures déjà identifiées ;
- et surtout **l'ordre d'exécution actuel**.

---

# 1. THÈSE PRODUIT

CUESHEET n'est pas :

- un clone d'OpenCode ;
- un terminal pour Claude/Codex ;
- un orchestrateur de sub-agents ;
- un IDE ;
- un chat avec accès au filesystem ;
- un projet dans lequel on ouvre des sessions.

CUESHEET doit devenir :

> **A living runtime that keeps human intent, machine understanding, software reality and evidence continuously synchronized.**

Ou, en termes plus opérationnels :

```text
HUMAN INTENT
     ↓
CUESHEET
     ↓
UNDERSTAND THE WORLD
     ↓
DETERMINE WHAT MUST HAPPEN
     ↓
ALLOCATE THE RIGHT INTELLIGENCE
     ↓
CHANGE REALITY
     ↓
PROVE THE RESULT
     ↓
KEEP HUMANS SYNCHRONIZED
     ↓
LEARN FROM REAL EXPERIENCE
```

Le développement logiciel est le premier domaine d'application.

Le modèle peut potentiellement s'étendre beaucoup plus loin.

---

# 2. LA RUPTURE FONDAMENTALE : WORLD > PROJECT > SESSION

CUESHEET ne doit jamais imposer le modèle :

```text
select project
↓
open session
↓
load context
↓
work
↓
close session
↓
select another project
```

Cette frontière doit disparaître.

CUESHEET existe au niveau du **World**.

```text
                         WORLD
                           │
       ┌───────────────────┼───────────────────┐
       ↓                   ↓                   ↓
    Projects            Knowledge          Capabilities
       │                   │                   │
 repos/apps             concepts             tools
 services               decisions            skills
 packages               evidence             MCP
 documents              artifacts            models
       │                   │                   │
       └───────────────────┼───────────────────┘
                           ↓
                        CUESHEET
                           ↕
                         HUMAN
```

Le user doit pouvoir lancer CUESHEET depuis `~`.

Puis dire :

> « Va voir mon projet Siri. »

CUESHEET doit retrouver IntentLane.

Puis :

> « Regarde aussi si Kollio est concerné. »

Même conversation.

Puis :

> « Cherche sur internet ce qu'Apple a changé. »

Même conversation.

Puis :

> « Fais-moi un document avec les conséquences. »

Même conversation.

Puis :

> « Applique ce qui vaut le coup. »

Même conversation.

Aucun changement de cwd visible.

Aucune « nouvelle session IntentLane ».

---

# 3. ZERO MODES

Pas de :

```text
Chat | Plan | Build | Debug | Research
```

Ce sont des stratégies internes.

L'utilisateur parle.

CUESHEET détermine s'il faut :

- répondre ;
- réfléchir ;
- chercher sur le web ;
- inspecter le World ;
- retrouver un projet ;
- créer un document ;
- coder ;
- lancer des tests ;
- créer des agents ;
- demander une décision ;
- attendre ;
- vérifier ;
- observer.

Exemple :

```text
"Pourquoi on avait fait ça ?"
→ knowledge

"Vérifie si c'est encore vrai."
→ research / reality

"OK change-le."
→ implementation

"Attends, pas la DB."
→ live steering

"Continue."
→ execution resumes
```

# 5. INTENT EST L'UNITÉ FONDAMENTALE

Pas le prompt.

Pas la tâche.

Pas le chat.

**Intent.**

Un intent peut contenir :

```yaml
intent:
  actor:
  goal:
  why:
  constraints:
  acceptance:
  assumptions:
  provenance:
  status:
```

Exemple :

```text
Intent:
allow project status transition

Why:
support certification workflow

Constraints:
- no breaking mobile API
- preserve audit history

Success:
- valid transitions work
- invalid transitions rejected
- old clients remain compatible
```

---

Et inversement, à partir d'un fichier ou d'une API :


# 7. INTENT DRIFT

CUESHEET doit détecter :

```text
ORIGINAL INTENT
      ≠
CURRENT WORK
```

Exemple :

```text
Original:
edit project title

Current modifications:
auth
organisation permissions
project creation
```

CUESHEET ne bloque pas aveuglément.

Il demande :

> Ces dépendances sont-elles réellement nécessaires ?

Si oui : étendre proprement l'impact.

Sinon : drift.

# 13. EPISTEMIC RUNTIME

Un des axes les plus importants.

Chaque claim important doit pouvoir être :

```text
● OBSERVED
◐ INFERRED
◇ ASSUMED
? UNKNOWN
```

Exemple :

```text
Mobile uses API v1
● OBSERVED
source: MobileContract.swift

External customers use API v1
? UNKNOWN
external consumers unavailable
```

Règle :

> **Inference may guide exploration. Evidence closes work.**

---

# 14. KNOWLEDGE HALF-LIFE

La mémoire n'est pas automatiquement vraie éternellement.

Une connaissance possède :

- provenance ;
- freshness ;
- supporting sources ;
- invalidators.

Si la source change :

```text
OBSERVED
↓
source changed
↓
STALE
↓
re-observe
```

Une mémoire ancienne fausse peut être plus dangereuse qu'une absence de mémoire.

---

# 15. SHARED ENGINEERING STATE

Principe fondamental :

> Material knowledge known by a human must become addressable by agents.

Et :

> Material knowledge discovered by an agent must become addressable by humans and relevant agents.

Mais surtout pas :

```text
send every conversation
to every agent
```

La mémoire doit être structurée.

# 21. MODÈLE ≠ AGENT

Très important.

Un worker ne doit jamais être :

```text

```

Mais :

```text
Worker A
├── work
├── intent
├── context
├── evidence
├── unresolved question
└── current compute
```

Le modèle est du compute interchangeable.

Providers initiaux importants :

- OpenCode Zen ;
- OpenCode Go ;
- puis autres providers/local.

Le catalogue de modèles doit idéalement être découvert dynamiquement.

Chaque worker peut utiliser un modèle différent.

# 23. FAILURE CLASSIFICATION

Différencier :

```text
TRANSIENT
RATE_LIMIT
QUOTA_EXHAUSTED
CONTEXT_OVERFLOW
AUTH
MODEL_UNAVAILABLE

```

Réactions différentes.

Pas « retry x3 » universel.

---

# 24. CIRCUIT BREAKER + GLOBAL BACKPRESSURE

Si 30 workers utilisent Zen et Zen commence à répondre 429 :

ne pas laisser 30 workers retenter individuellement.

Le runtime voit la pression globale.

Il peut :

- diminuer la concurrence ;
- rerouter ;
- retarder le non-critique ;
- réserver les capacités restantes au critical path.

# 25. ADAPTIVE MODEL ROUTING

Principe :

```text
WORK UNIT
↓
requirements
↓
router
↓
capability
```

Exemples :

```text
grep/imports
→ deterministic

small summary
→ cheap model

coding
→ coding model

architecture ambiguity
→ reasoning model

tests
→ tool

hard failure
→ escalation
```

Règle :

> **Deterministic before probabilistic. Cheap before expensive. Local before global. Escalate on evidence.**

Et downgrade ensuite si le problème devient simple.

# 29. ELASTIC WORKFORCE

# 37. HUMAN DELTA

Ne pas expliquer tout.

Expliquer uniquement ce qui change le modèle mental nécessaire.

Exemple :

```text

```

# 38. CONFIRMATION BY EXCEPTION

Pas :

> « Est-ce que j'ai compris ? »

à chaque étape.

Niveaux :

```text

→ silent

→ surface

2 important assumption
→ surface and continue

3 irreversible / genuinely ambiguous
→ block for decision
```
