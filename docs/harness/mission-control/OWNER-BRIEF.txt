# CUESHEET MISSION CONTROL

## 0. Mission

Design and build the first bounded vertical slice of a Cuesheet MCP App.

Product idea:

> ChatGPT, Claude and other MCP App hosts can become portable human-control surfaces for Cuesheet while Cuesheet remains the execution harness.

The MCP App is NOT Cuesheet itself.

Cuesheet remains responsible for:

- intent;
- execution state;
- workers;
- models;
- tools;
- worktrees;
- verification;
- evidence;
- recovery;
- permissions;
- durable state.

The MCP App is a projection of that state for a human.

Its purpose is:

**SEE → UNDERSTAND → STEER → APPROVE**

Do not duplicate Cuesheet's terminal UI.

Do not build a dashboard for the sake of having a dashboard.

Do not expose every internal event.

---

# 1. Core user story

A user is talking to ChatGPT or Claude.

They say:

> Continue IntentLane until the next real human gate.

The assistant invokes Cuesheet through MCP.

Cuesheet starts or continues the mission.

The conversation displays:

```text
┌─────────────────────────────────────────────┐
│ INTENTLANE                         RUNNING  │
│                                             │
│ Reach the next real human gate              │
│                                             │
│ ███████████████░░░░                         │
│                                             │
│ ✓ Repository reconciliation                 │
│ ✓ Fixture verification                      │
│ ● CI verification                           │
│ ○ Siri acceptance                           │
│                                             │
│ 2 workers · 8m · 41k tokens                 │
│                                             │
│ No action required                          │
│                                             │
│                          Inspect             │
└─────────────────────────────────────────────┘
```

The user does not need to watch Cuesheet.

They continue talking normally.

# 2. Human interruption

While Cuesheet works, the user says:

> Don't touch the MCP work. Apple proof only.

That instruction must enter the SAME active Cuesheet mission.

No new independent chat-agent universe.

Expected flow:

ChatGPT/Claude
→ MCP `steer_mission`
→ Cuesheet shared live context
→ semantic impact analysis
→ affected execution nodes reconciled
→ unaffected work preserved

The MCP App updates:

```text
┌─────────────────────────────────────────────┐
│ INTENTLANE                         UPDATED  │
│                                             │
│ New constraint                              │
│                                             │
│ "Apple proof only. Do not activate MCP."    │
│                                             │
│ Impact                                      │
│                                             │
│ ✓ Current CI work preserved                 │
│ ✓ Fixture work preserved                    │
│ × MCP exploration excluded                  │
│                                             │
│ Execution continued                         │
└─────────────────────────────────────────────┘
```

This must use Cuesheet's existing live-context semantics.

Do not implement a separate MCP-specific queue.

# 4. Product philosophy

## Conversation for intent

Use natural language for:

- objectives;
- corrections;
- constraints;
- questions;
- reprioritization.

## UI for state

Use UI for:

- progress;
- workers;
- dependencies;
- evidence;
- failures;
- costs;
- human gates.

## UI for precision

Use UI when the user needs to:

- select;
- compare;
- inspect;
- approve;
- reject.

## Cuesheet for execution

Never move orchestration logic into the MCP App.

---

# 5. First MCP capability set

Do NOT expose 50 tools.

Implement/specify only the minimum useful surface.

## `list_missions`

Read-only.

Returns active/recent missions.

## `get_mission`

Read-only.

Returns one mission's semantic state.

## `start_mission`

Mutation.

Starts a bounded Cuesheet objective.

Must preserve existing Cuesheet admission/policy.

## `steer_mission`

Mutation.

Adds a human correction/constraint to an existing mission.

Must use Cuesheet's live-context path.

No separate message queue.

## `stop_mission`

Mutation.

Explicit human cancellation.

## `get_human_delta`

Read-only.

Returns only information requiring human understanding/action.

Do not initially expose low-level worker-control tools.

---

# 6. Do NOT initially expose

No:

`spawn_agent`

`kill_agent`

`change_worker_model`

`run_shell`

`merge_worktree`

`approve_git_diff`

`edit_memory`

Mission Control v0 is goal-level.

The user controls intent.

Cuesheet controls execution topology.

Advanced controls may later appear behind Inspect if evidence demonstrates demand.

# 7. Canonical mission model

Do not invent a second execution state.

Project Cuesheet's existing state.

The MCP representation should conceptually expose:

```yaml
mission:
  id:
  project:
  objective:

  state:
    running | blocked | failed | human_required | verified | completed

  progress:
    completed:
    active:
    pending:

  workers:
    active:
    total:

  resources:
    elapsed:
    tokens:
    cost:

  evidence:
    verified:
    failed:
    unknown:

  humanDelta:
    required:
    reason:
    actions:

  updatedAt:
```

Use actual available data.

If cost is unknown:

`unknown`

Never estimate fake precision.

# 8. Evidence classes

The UI must visually distinguish:

VERIFIED

OBSERVED

RUNNING

FAILED

BLOCKED

UNKNOWN

HUMAN_REQUIRED

Do not render every state as green checkmarks.

A model response is not VERIFIED.

A worker saying DONE is not VERIFIED.

Use Cuesheet evidence semantics.

# 9. Three UI levels

Mission Control has exactly three initial views.

## A. Mission Card

Default inline view.

Purpose:

> "Do I need to care right now?"

Contains:

- project;
- objective;
- mission state;
- semantic progress;
- current phase;
- worker count;
- elapsed time;
- token/cost only when known;
- Human Delta indicator.

No logs.

No internal IDs unless needed.

---

## B. Mission Inspector

Expanded/fullscreen.

Purpose:

> "What is actually happening?"

Structure:

```text
MISSION
│
├ Objective
│
├ Execution graph
│
├ Workers
│
├ Evidence
│
├ Decisions
│
├ Failures / recovery
│
└ Human Delta
```

Example:

```text
IntentLane / Apple proof

                         ┌ CI verifier ✓
Repository reconciliation┤
                         └ OpenSpec verifier ✓

Fixture ─────────────────── ✓

NetNewsWire reproduction
        │
        ├ build ✓
        ├ metadata ✓
        └ Siri ○ HUMAN

Workers

Verifier
Claude Sonnet
completed
14k tokens

Repository investigator
OpenCode
completed
9k tokens
```

Graph is semantic.

Do not display every internal runtime event.

---

## C. Human Delta

Focused decision/action surface.

Purpose:

> "What specifically needs me?"

Example:

```text
HUMAN DELTA

Decision required

Two implementation strategies remain
equally consistent with the product spec.

A
Keep local storage only

B
Introduce remote synchronization

Why Cuesheet stopped

This changes product behavior and cannot
be resolved from existing evidence.

[Choose A]   [Choose B]
```

This should be rare.

If Human Delta appears constantly, Cuesheet autonomy is failing.

# 11. Host adaptation

Mission Control must not require identical pixels across hosts.

The same semantics may render differently in:

- Claude;
- ChatGPT;
- future MCP hosts;
- text-only MCP clients.

Maintain:

same mission
same state
same evidence
same available actions

Allow:

different typography
different spacing
different host chrome
different responsive layout

---

# 12. Graceful degradation

Mission Control MUST remain useful without MCP UI support.

Example text fallback:

```text
IntentLane — HUMAN_REQUIRED

Objective:
Reach the next Apple proof gate.

Machine complete:
- build
- fixture
- metadata
- automated tests

Human required:
Run the Siri acceptance procedure.

No machine work remains before this gate.
```

The tool semantics cannot depend on the iframe.

---

# 13. Structured content

Separate model context from UI payload.

The model needs:

- semantic summary;
- important state;
- human requirement;
- available high-level actions.

The UI may need:

- execution graph;
- complete worker list;
- evidence records;
- timeline;
- metrics.

Do not inject full UI datasets into model context unnecessarily.

---

# 14. Security

Mission Control is a control surface.

Treat mutations accordingly.

`start_mission`

`steer_mission`

`stop_mission`

must go through existing Cuesheet authority/admission mechanisms.

The MCP App iframe must never independently grant execution authority.

Never trust:

- project path from UI without validation;
- worker IDs supplied by arbitrary content;
- model-generated permissions;
- client-side confirmation alone.

---

# 15. Human confirmation

Confirmation belongs to the tool/host security path.

The UI may DISPLAY:

preview
impact
risk

but cannot be the sole authority for a sensitive mutation.

# 30. Definition of Done

v0 is DONE only when:

1. a real Cuesheet mission is represented through MCP;
2. the Mission Card reflects real state;
3. a human can steer that SAME mission through conversation/MCP;
4. Cuesheet incorporates the steering without a message queue;
5. real verification state is shown;
6. Human Delta appears when Cuesheet genuinely reaches a human boundary;
7. a non-UI MCP client receives a useful textual fallback;
8. sensitive mutations remain controlled by Cuesheet/tool authority;
9. no fake worker/progress/cost data is displayed;
10. the demonstration is reproducible.

The product thesis is:

> **Let agents work. Show humans only what matters.**

And the UX thesis is:

> **Conversation controls intent. Mission Control exposes reality. Cuesheet executes.**

Je pense que **c'est celui-là qu'il faut donner à ton agent**, parce qu'il ne crée pas un troisième projet sorti de nulle part : il utilise Cuesheet comme moteur réel et MCP Apps comme nouvelle surface.

Et surtout, la démo est extrêmement compréhensible : **tu demandes quelque chose depuis Claude/ChatGPT, tu continues à discuter pendant que Cuesheet travaille, tu corriges sa mission en direct, et l'interface n'interrompt ta conversation que lorsqu'une vraie décision humaine est nécessaire.** C'est beaucoup plus fort qu'un simple dashboard d'agents.
